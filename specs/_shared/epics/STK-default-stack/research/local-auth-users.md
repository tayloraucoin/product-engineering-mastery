# How should users exist in a local database when sign-in runs on a hosted project, and what is the clean form of the mimicry the three repos patched in?

Researched 2026-10-03 by Warden (security and privacy), consulting Mason on placement and the migration set and Millwright on running Supabase locally. All code was read read-only from the three product repos. No `.env` file was opened: only the `.env.example` files were read. Claims are labelled **verified** (read from code or a primary source, with a date and a version), **secondary** (someone else said so) or **judgment** (mine).

## Answer

Both modes run the local database on Supabase's own Postgres image, through the Supabase CLI, so the starter ships no hand-made copy of Supabase's `auth` schema. Mode A (local data, sign-in against hosted staging) runs `supabase db start`, which starts the database container only. That image already creates the `anon`, `authenticated` and `service_role` roles, the default grants, an `auth` schema with `auth.users`, and `auth.uid()`. The only mimicry left is a **mirror**: when someone signs in on staging, it writes their `id` and `email` into the local `auth.users`, and the existing `handle_new_user` trigger then creates their `public.users` row. The mirror lives in one file, `packages/db/src/local-auth-mirror.ts`, and is called from one place, the `@pem/auth` request seam. It can write only to a database that **no Auth server has ever set up**, meaning `auth.identities` is absent, and that carries a marker table that only the local apply script creates. Both conditions sit inside the `INSERT` statement itself, so the statement cannot touch staging, production, or a full local stack even if every environment variable is wrong.

The hand-edited migration `0000` disappears for a different reason. drizzle-kit 0.31.10 generated the `auth` schema and table only because the repos **exported** their `auth.users` mirror from the schema entry. Importing `authUsers` from `drizzle-orm/supabase` without exporting it gives a clean foreign key. I verified this by running drizzle-kit, not by reading docs.

Mode B (fully local) runs `supabase start` with Drizzle still owning `public`. CLI migrations and seeds are switched off in `config.toml`, users are created through the local Admin API, and the mirror does nothing.

Which mode a machine is in depends only on the values of the `_LOCAL` auth variables (a staging URL or `127.0.0.1:54321`), so application code has a single code path.

Recommended default: **mode A**. Revisit when a second developer works for longer than a week, or when a product needs Auth behaviour the mirror cannot reproduce locally. Taylor decides `[NEEDS DECISION]`: the CLI is the default local database runner in both modes, and its full stack is the mode B option.

With hosted sign-in, sign-ups happen in the **staging** database, so the local database never hears about them.

## 3. Mode A: local data, hosted staging sign-in

### 3.1 The migration set needs no `auth` objects

I ran drizzle-kit 0.31.10 and drizzle-orm 0.45.2 from Synapse's `node_modules` in a scratch folder on 2026-10-03, using `schemaFilter: ["public"]` and `generate`, with four layouts of the same `users` table referencing `auth.users`:

| Variant | Layout                                                                             | Generated                                                                         |
| ------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| a       | A local `auth.ts` mirror, exported from the schema entry (the layout of S2 and C1) | `CREATE SCHEMA "auth"`, `CREATE TABLE "auth"."users"`, the table, the foreign key |
| b       | The same mirror, imported by `users.ts` but **not exported**                       | The table and the foreign key only. A second `generate` reports no changes        |
| c       | `import { authUsers } from "drizzle-orm/supabase"`, not exported                   | The table and the foreign key only                                                |
| d       | The same `authUsers`, re-exported from the schema entry                            | `CREATE TABLE "auth"."users"` (no schema statement), which would fail on hosted   |

Label: **verified by execution.** The source confirms why: drizzle-kit collects tables and schemas from module exports only (`bin.cjs:16727-16768`). Drizzle's RLS page says these objects are treated as existing. That holds for the roles, which are declared `.existing()`, but not for `authUsers`, which is a plain table (`drizzle-orm/supabase/rls.js`). The page is accurate only for variant c.

**Design:** delete the local mirror file. `packages/db/src/schema/user/users.ts` imports `authUsers` from `drizzle-orm/supabase` and never exports it. A check, `packages/db/scripts/check-migrations.ts`, run in `yarn verify`, fails on any DDL against `"auth".` in `migrations/`, so variant d cannot come back silently. This removes S1, S2, C1 and the "re-apply after regenerate" step in both SETUP files.

### 3.2 The local database is the Supabase image, started without its services

`yarn db:local` runs `supabase db start --workdir packages/db`, which starts the database container only (CLI reference, v2.119.0, read 2026-10-03, verified). The image provides the roles, default privileges, `auth.users` and `auth.uid()` (verified, image init scripts, `develop`, latest tag `v17.11.0.003-cli` of 2026-10-02). It also matches hosted on the restrictions that matter: `postgres` lost `CREATE` on schema `auth` (image migration `20250421084701`). A migration that tries to create something in `auth` therefore fails locally the same way it fails on staging, which a bare Postgres would never show. This removes S6 and H2. Label: verified (image), judgment (that this parity is worth one container).

### 3.3 The one mimicry file: `packages/db/src/local-auth-mirror.ts`

It exports three things and owns no DDL in `auth`:

- `mirrorHostedUser(db, { id, email }, target)`: the only writer to `auth.users` in the codebase. `target` holds the resolved tier, database URL and auth URL, passed in from `env.ts`. The module never reads `process.env` (conventions rule 6).
- `applyLocalAuthMirror(url)`: creates the marker `local_auth_mirror.enabled`, a one-row table recording when and by whom it was applied.
- `isLocalAuthServer(authUrl)`: true when the auth URL's host is loopback. Section 5 builds on it.

The guard has four conditions. The first three are cheap pre-checks; the last two are in the SQL, where they hold regardless of configuration:

1. The tier is `local`.
2. The runtime database host is loopback (`127.0.0.1`, `localhost`, `::1`).
3. The auth URL is **not** loopback. If it were, this would be mode B, where the Auth server creates the user and the mirror has nothing to do.
4. In the statement itself:

```sql
-- Synthetic values; the real call binds the signed-in session's id and email.
INSERT INTO auth.users (id, email)
SELECT '00000000-0000-4000-8000-000000000001'::uuid, 'dev@example.test'
WHERE to_regclass('auth.identities') IS NULL           -- no Auth server has ever migrated this database
  AND to_regclass('local_auth_mirror.enabled') IS NOT NULL  -- the local apply script ran here
ON CONFLICT (id) DO UPDATE SET email = EXCLUDED.email
  WHERE auth.users.email IS DISTINCT FROM EXCLUDED.email;
```

`auth.identities` is created by the Auth server's own migrations (`supabase/auth` `20210909172000_create_identities_table`), and the image never creates it (verified, 2026-10-03). Staging, production and a mode B stack all have it, so on any of them the statement inserts zero rows even through an SSH tunnel to `localhost`. The marker covers the remaining case: a Supabase-image database someone else started. `applyLocalAuthMirror` refuses a non-loopback host and any database that has `auth.identities`. Only `id` and `email` are written, the two columns every `auth.users` variant has, which fixes S4. The `ON CONFLICT ... WHERE` clause fires the existing email-sync trigger only on a real change. The mirror **never** writes `public.*`, roles, entitlements or flags: the trigger creates `public.users` exactly as it would in production, and C3 and H3 have no place here. Label: judgment (design); verified (each catalog fact it relies on).

**Called once.** `@pem/auth`'s request seam (the one function that turns a session into an `AuthContext`) calls `mirrorHostedUser` after `getUser`. A per-process `Set` of mirrored ids makes later requests free. On hosted tiers, condition 1 returns before any SQL runs. This replaces S5 and C4. `@pem/auth` importing `@pem/db` is downward in the house layer order, so the boundary holds (Mason, consulted). `[ASSUMPTION: the starter keeps db below auth, as both recent repos do.]`

### 3.4 Seeds and reset in mode A

- No staging secret on the laptop. `db:seed-users` refuses when the auth URL is not loopback, so a local-tier command can never write to a hosted project (fixes S8). Synthetic staging accounts (`.test` domains only) are created once by a person running `DATABASE_ENVIRONMENT=staging yarn db:seed-users`, under the existing rule that only a human touches a hosted tier.
- `db:seed` looks the account up by email, as Synapse does today. In mode A the developer signs in once after a reset, the mirror creates the row, and then `db:seed` runs. That costs one sign-in per reset. Judgment: an acceptable price for keeping the staging secret off the machine.
- `db:reset` runs `supabase db reset --workdir packages/db` (which recreates the whole database, including `drizzle` and the marker), then `db:migrate`, `db:setup`, `db:local-auth`, `db:seed-users` and `db:seed`. The two auth steps each skip themselves in the wrong mode, which fixes S7. `[ASSUMPTION: supabase db reset works when only db start is running; verify in the first ticket. Fallback: drop the drizzle, public and local_auth_mirror schemas.]`
- In the staging project's Auth settings, add `http://localhost:3000/**` to the redirect URLs. **Consider:** never on the production project.

There is no mode variable. The tier stays `local`, and the mode is whatever the `_LOCAL` values point at, following the existing suffix grammar (`_LOCAL`, `_STAGING`, unsuffixed for production):

## 7. Recommendation

**Default: mode A.** It matches Taylor's daily work, needs only the staging project that already exists plus one container, keeps every hosted secret off the machine, and confines the mimicry to one guarded file. **Mode B** is documented in the guide for a second developer, offline work, and any product that needs Auth behaviour locally. `[NEEDS DECISION]` Taylor confirms the default and the CLI's role: the default local database runner in both modes, with the full stack as an option.

**Residual risk, stated plainly:**

- Sign-ups, deletions and Auth hooks on staging are not replayed locally. Email changes reach the local database on the next request.
- Realtime and policies keyed on `auth.uid()` cannot be exercised locally in mode A.
- Staging identities are copied onto laptops. That is acceptable only while staging holds synthetic `.test` accounts. **Should-fix** if any real tester is ever on staging (Millwright's rule: nothing resembling real customer data flows down to a developer machine).

**Revisit when** a second developer works in the repo for more than a week; a product adopts Auth hooks, MFA, Realtime on user tables, or a trigger that reads `auth.users` columns beyond `id` and `email`; or `local-auth-mirror.ts` needs a second edit. Any one of these makes mode B the default.
