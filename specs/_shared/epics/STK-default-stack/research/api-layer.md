# What does the API layer between the apps and the data do in the house stack, when is it the right tool and when is it more than a product needs?

## Answer

Ship `@pem/api` on tRPC 11.x in the starter as a **removable module**: wired, documented and lint-bounded, with a removal manifest so that a product with no second client and no client-cached reads can delete it and leave no file, variable or dependency behind. This depends on one move that matters more than the tRPC choice itself: take the services out of the transport package (`@pem/services`, sitting below `@pem/api`) so that deleting tRPC never deletes business logic. The tradeoff in one sentence: you keep the rail you know and that a second client can reach, and you pay for a module that some products will delete on day one. Revisit trigger: change the ruling to "default" if a native or second-web client is scheduled in a briefing; change it to "absent" if the first two products ported from the starter both remove the module before first deploy; re-open it entirely if tRPC publishes a v12 that changes the `@trpc/tanstack-react-query` contract, or if Next.js documents Server Functions as sanctioned for cached, parallel data fetching (as of Next.js 16.3.8 docs, last updated 2026-06-17, they are documented for mutations, dispatched one at a time). (judgment)

### 1. The mental model

Everything between a screen and Postgres is one of four **entry rails**. Rails are thin: they authenticate, validate with a shared Zod schema, call one service function, and translate the result into what their transport speaks. All logic lives once, in `services/<domain>/`, and every caller, screen or not, enters there.

```
                         SCREENS (Next.js App Router)
        +-------------------------------+------------------------------+
        | Server Component              | Client Component             |
        +-------------------------------+------------------------------+
           |            |                     |              |
     (1) RSC direct  (4b) tRPC          (2) Server       (4a) tRPC over HTTP
         read         server caller         Action           (TanStack Query)
           |          (in-process)       POST, action ID          |
           |            |                     |                   v
           |            |                     |        (3) Route Handler
           |            |                     |            app/api/trpc/[trpc]/route.ts
           |            |                     |                   |
           |            |                     |   (3) other Route Handlers:
           |            |                     |       webhooks, cron, OAuth callback,
           |            |                     |       AI streaming, public API
           v            v                     v                   v
        +-------------------------------------------------------------------+
        | seam: auth check (procedure tier / action wrapper) + Zod validator |
        |                     @pem/validators (one schema, every rail)       |
        +-------------------------------------------------------------------+
                                       |
                                       v
        +-------------------------------------------------------------------+
        |   services/<domain>/   plain async fns (ctx, input) -> data | err   |
        +-------------------------------------------------------------------+
                                       |
                                       v
        +-------------------------------------------------------------------+
        |   @pem/db  Drizzle + rls.ts bridge (sets user and role per tx)      |
        +-------------------------------------------------------------------+
                                       |
                                       v
                          Postgres (Supabase) with RLS deny-by-default

  NON-SCREEN CALLERS, same services, never through a screen rail:
   Stripe webhook --> Route Handler --> services/billing
   Vercel Cron    --> Route Handler --> services/<domain>
   Job worker     --> (direct import) --> services/<domain>
   AI chat        --> Route Handler (stream) --> services/ai + services/<domain>
   2nd web app    --> tRPC over HTTP (or its own rails over shared services)
   React Native   --> tRPC over HTTP, bearer token
   Third party    --> Route Handler (REST/OpenAPI), never the internal RPC
```

`proxy.ts` (the Next.js 16 name for middleware, which runs on the Node.js runtime) sits in front of all of it and only refreshes the session; it is not an authorization layer.\[1\] (verified, Next.js 16 release post; judgment on role)

**(1) Server Component direct read.** An async Server Component awaits a service call during render, and React streams the result as HTML and an RSC payload. There is no endpoint, no client cache and no client bundle cost. Next.js 16 adds Cache Components (`use cache`) and tag-based invalidation on top. Its weakness is that the data is fixed at render time: to change it you re-render the route (navigate, `refresh`, or invalidate a tag from a mutation). Problem it solves: _getting server data into first paint with zero API surface._ (verified as to mechanism, Next.js 16.3.8 docs, 2026-06-17; judgment on framing)

**(2) Server Action (React Server Function).** Mark a function `'use server'` and the compiler replaces it in client bundles with an action ID plus a dispatcher that POSTs back to the page. When the action calls `updateTag`, `revalidatePath` or `refresh`, the same response carries the return value and a freshly rendered RSC payload, so the screen updates in one round trip. `<form action>` works before JavaScript loads (progressive enhancement), and `useActionState` and `useOptimistic` handle pending and optimistic state. Costs, per the 16.3.8 docs: actions are dispatched one at a time per client, so `Promise.all` does not parallelize them; every action is a public POST that anyone can send; the framework does an Origin/Host CSRF check, caps the body at 1 MB by default, encrypts action IDs and closure variables, and rotates IDs at most every 14 days, so a stale tab can hit "Failed to find Server Action".\[2\] Problem it solves: _a form or button mutation that refreshes the server-rendered page, with no endpoint to name._ (verified, nextjs.org/docs/app/guides/server-actions, version 16.3.8, last updated 2026-06-17)

**(3) Route Handler.** `app/**/route.ts` exports `GET`, `POST` and so on, and works on Web `Request`/`Response`. It is a real URL with a stable contract that any HTTP client can call: browsers, native apps, Stripe, Vercel Cron, OAuth providers, third parties. It is the only rail that gives you full control of the raw request body, headers, status codes and streamed responses. tRPC itself is mounted on one of these.\[3\] Problem it solves: _anything that is not your own React tree calling in, or anything that needs a raw HTTP contract._ (verified for mechanism, trpc.io App Router setup note; judgment for framing)

**(4) tRPC procedure.** A typed RPC layer: `router({ note: { list, create } })` on the server, and the client imports only `type AppRouter`, so there is no codegen. On the wire it is HTTP through the fetch-adapter Route Handler at `app/api/trpc/[trpc]/route.ts` (4a). In Server Components the same procedures run in-process through a server-side proxy/caller (4b) and can prefetch into the TanStack Query cache, which the client then hydrates.\[3\]\[4\]\[5\] Middleware gives procedure tiers (public, protected, admin) in one place. Problem it solves: _typed, cached, parallel reads and writes from any TypeScript client, the second web app and the native app included, against one contract._ (verified, trpc.io v11 announcement 2025-03-21 and App Router setup page, 11.x, verified 2026-10-03)

The smallest pair that shows the difference (synthetic; API shape per trpc.io 11.x docs, verified 2026-10-03; not compiled):

```ts
// Server Action + shared schema: a mutation; the page re-renders with fresh data
"use server";
export async function createNote(raw: unknown) {
  const ctx = await requireUser(); // wrapper does auth
  const input = createNoteInput.parse(raw); // @pem/validators
  await notes.create(ctx, input); // @pem/services/notes
  updateTag("notes"); // RSC re-render in same response
}
```

```ts
// tRPC: same schema and service, plus a typed, cached read any TS client can call
export const noteRouter = router({
  list: protectedProcedure.query(({ ctx }) => notes.list(ctx)),
  create: protectedProcedure
    .input(createNoteInput)
    .mutation(({ ctx, input }) => notes.create(ctx, input)),
});
// client component
const trpc = useTRPC();
const list = useQuery(trpc.note.list.queryOptions());
const create = useMutation(
  trpc.note.create.mutationOptions({
    onSuccess: () =>
      qc.invalidateQueries({ queryKey: trpc.note.list.queryKey() }),
  }),
);
```

Read the difference this way: the Server Action invalidates the _server-rendered page_; the tRPC call invalidates a _client cache entry_. If a product's screens are server-rendered and re-rendered on mutation, the first is enough. If a product has interactive client state that lives across navigations, or a client that is not this Next.js app, you need the second. (judgment)

### 3. The case for and against tRPC as the house default

**For, at full strength.** The house has shipped two products on tRPC, with services under `api/services/<domain>`, a boundaries lint, and `hooks` consuming the typed seam. That is a convention Taylor and the agent already use, and Taylor ruled on 2026-10-03 that a convention set in advance beats one invented per project. One default rail means the agent never has to choose between a Server Action, a Route Handler and a direct read for an ordinary read or write: it writes a procedure, and the exceptions are listed. tRPC 11 is stable and well-documented, and its docs ship agent skills (`npx @tanstack/intent@latest install`) and an `llms.txt`, so an agent can reason about it.\[3\] It is the only rail of the four that a React Native client and a second web app can call with inferred types and no codegen, and that is the exact failure that killed Mason's earlier startup: web and native drifting apart because native grew its own API shapes. Server Actions cannot cache reads, cannot run in parallel from one client, and are not a documented contract for anything outside this Next.js build. Their IDs rotate between builds, so they cannot be the API a native app calls. tRPC's middleware tiers give deny-by-default authorization one home at the seam, on top of RLS. And the exit is cheap: T3 itself chose it because procedures are "just functions that are trivial to move off".\[18\] If services are already transport-free, you can remove tRPC by deleting thin wrappers.

**Against, at full strength.** Next.js 16 has made the platform rails good enough for most single-app products: RSC direct reads with Cache Components for reads, Server Actions with `updateTag` for writes that come back with a fresh page in one round trip, and progressive enhancement that tRPC does not give. Adding tRPC on top of that runs two data paths (RSC reads and TanStack Query cache), two invalidation models (`updateTag` and `invalidateQueries`), a hydration step with its own pitfalls, and about six setup files and five packages before the first endpoint. The starter's own rules say nothing exists before its first consumer. A pre-built API layer in a starter is code with no product exercising it, and an unexercised seam rots without anyone noticing. The upgrade history is real: v10 to v11 forced a TanStack Query v5 migration in the same move, the classic hooks client is now second-class, and the Server Actions bridge is still `experimental_`.\[5\]\[16\]\[19\] Every major of tRPC is also, in effect, a major of TanStack Query. For a marketing site or a single internal tool, tRPC is overhead that the agent will still dutifully maintain. And "duplicate, then remove" puts the cost of every default module on the products that don't want it.

**Where this lands (judgment).** Both cases are right about different products. The case for is decisive wherever a second client exists or client-side cached state matters. The case against is decisive for marketing sites and server-rendered single apps. What resolves it is not tRPC at all: it is whether services survive tRPC's removal. If services survive, tRPC can ship as a module that is cheap to keep and cheap to delete, so "removable module" dominates both "default" and "absent".

### 4. Use cases

| Use case                                         | Correct rail                                                                                   | tRPC verdict                | Why                                                                                                                                      |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------- | --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Marketing site                                   | RSC direct reads (`use cache`); Server Action for the contact/newsletter form                  | Overkill                    | No client cache, no second consumer; progressive enhancement matters more.                                                               |
| Single web app, mostly server-rendered           | RSC reads plus Server Actions; tRPC for interactive client-state screens                       | Acceptable                  | Correct once you have filters, infinite lists or optimistic client state; overkill for CRUD that re-renders the page.                    |
| Web app plus a second web app sharing procedures | tRPC router in `@pem/api`, both apps call it (or each app's rails over shared `@pem/services`) | Correct                     | One typed contract; if both apps deploy separately, one hosts the router and the other calls it over HTTP.                               |
| Web app plus React Native app                    | tRPC over HTTP with bearer-token auth                                                          | Correct                     | Native cannot rely on Server Actions; tRPC is the typed HTTP contract both share (create-t3-turbo does exactly this).\[20\]\[21\]        |
| Public or third-party API consumers              | Versioned Route Handlers with OpenAPI                                                          | Wrong tool                  | tRPC's wire format is an internal RPC; `@trpc/openapi` is alpha in 11.x.\[11\] Never expose the internal router as the public API.\[10\] |
| Webhooks (Stripe)                                | Route Handler, signature check on the raw body, then service                                   | Wrong tool                  | The caller is Stripe, not a TypeScript client; you need raw body and status-code control.                                                |
| Streaming AI responses                           | Route Handler with the AI SDK's `streamText` and UI message stream, `useChat` on the client    | Wrong tool (as the default) | The AI SDK owns the chat stream protocol; tRPC streaming works but duplicates it.                                                        |
| Background jobs and cron                         | Vercel Cron to a Route Handler checking `CRON_SECRET`; workers import services directly\[22\]  | Wrong tool                  | No client and no types to infer; going through tRPC adds HTTP and context faking for nothing.                                            |

### 5. The service layer, independent of the transport

**What `services/<domain>/` is.** Plain async functions: `create(ctx, input)`, where `ctx` carries the authenticated user (id, role) and a `db` or transaction handle from `@pem/db`'s RLS bridge, and `input` is already validated. They return data or throw typed domain errors (`NotFound`, `Forbidden`, `Conflict`, `Invalid`) from one small error module. They contain no `Request`, no `cookies()`/`headers()`, no `TRPCError`, no `revalidatePath`/`updateTag`, no `redirect`. Multi-step work (charge, then grant entitlement, then email) lives here exactly once, so the Stripe webhook, a Server Action and a tRPC procedure all call the same function. (judgment; matches Mason's thin-seam rule)

**What validators are.** Zod schemas in `@pem/validators`, defined once and imported by the form (client-side), the Server Action, the tRPC `.input()`, and the Route Handler. Services may re-assert invariants but never redefine shape. (judgment; tech-stack.md: "one schema shared by forms and procedures")

**Where authorization lives.** Two layers on purpose. The database is the guarantee: RLS deny-by-default, with `rls.ts` setting user and role per transaction. The seam is the gate: tRPC procedure tiers (`publicProcedure`, `protectedProcedure`, `adminProcedure`), or the equivalent action wrapper for Server Actions, and an explicit check at the top of each Route Handler (`CRON_SECRET`, Stripe signature, API key). The Next.js docs say the same about actions: treat each one as a public endpoint and check auth inside it, because render-time gating is not a security boundary.\[2\] (verified for Next.js guidance, 16.3.8 docs 2026-06-17; judgment for the split)

**Error mapping at the boundary.** One adapter per rail, written once: tRPC maps `NotFound`/`Forbidden`/`Conflict`/`Invalid` to `TRPCError` `NOT_FOUND`/`FORBIDDEN`/`CONFLICT`/`BAD_REQUEST` in an error-formatting middleware; Server Actions map them to a typed result (`{ ok: false, code }`) for `useActionState`; Route Handlers map them to HTTP 404/403/409/422. Services never know which one ran. (judgment)

**Can the starter keep services and validators and make the transport a later choice?** Yes, and it should, but only if services leave the transport package. In CC and Synapse, services live inside `api` (`api/services/<domain>`), so deleting `@cc/api` would delete the business logic with it. That fails the brief's metric. [PROPOSED] the layer order becomes:

`config -> constants / types / observability -> utils -> validators -> db -> auth -> (ai) -> services -> api (tRPC transport only) -> hooks -> ui -> apps`

with these lint-enforced rules:

- `@pem/services` may import `validators`, `db`, `auth`, `ai`, `observability`, `utils`, and nothing from `next/*`, `@trpc/*` or `react`.
- `@pem/api` contains only `init.ts` (context and tiers), `routers/<domain>.ts`, `root.ts` and the client and server entry points (`@pem/api/client`, `@pem/api/server`); every procedure body is a single service call.
- Route Handlers and Server Actions in `apps/*` import `@pem/services` and `@pem/validators` directly, and must not import `@pem/api` internals.
- `@pem/hooks` holds headless hooks that do not import `@pem/api`. Query hooks that wrap procedures live in `@pem/api/react` or in the app, so that removing the transport does not cascade into `hooks`. [NEEDS DECISION] whether `@pem/hooks` may import `@pem/api` at all, or whether that edge is cut, as proposed.
- [NEEDS DECISION] the package name and location: `@pem/services` as its own package (proposed, because it gives the lint a package edge to enforce) or `packages/core/services/` folders.

With that split, the removal manifest for `@pem/api` is short and mechanical: `packages/api/`, `apps/*/app/api/trpc/`, the provider line in each `layout.tsx`, `apps/*/trpc/` if any, five dependencies, the boundaries-lint entries for `@pem/api`, and any `NEXT_PUBLIC_*` base-URL variable used only by the tRPC client. (judgment; the exact env variable names in the starter are not known, see Assumptions)

**What a React Native client needs from the server (Wainwright, consulted).** An HTTP endpoint with a stable contract. Server Actions are not one: their IDs are build artifacts that rotate, and no Next.js or Expo document found sanctions calling them from native. It needs bearer-token auth, not cookies: the context factory must accept `Authorization: Bearer <supabase access token>` as well as the cookie session, and resolve both to the same `ctx.user`.\[23\] It needs a typed client: tRPC's `createTRPCClient<AppRouter>` with `httpBatchLink`, and TanStack Query for cache, retry and, with a persister, queued mutations that survive process death. And it needs streaming caveats accepted: tRPC's own docs say `httpSubscriptionLink` on React Native needs `rn-eventsource-reborn`, `web-streams-polyfill` and `@azure/core-asynciterator-polyfill`.\[15\] Expo Router has its own `+api.ts` API routes (with `expo-server` runtime helpers since SDK 54, enabled by default in SDK 58 with server output).\[24\]\[25\] They are an option for an Expo-only product, but they would become a second server, and Mason's rule rejects that while a Next.js app exists. create-t3-turbo (Expo SDK 54, tRPC v11, Better Auth) is the reference pattern: the shared `api` package is consumed by both apps, and the Next.js app must be deployed for the Expo app to reach it.\[20\]\[26\] (verified for tRPC RN ponyfills, Expo API routes and create-t3-turbo README, as of 2026-10-03; judgment for the rest; offline persistence not verified this session)

### 6. Recommendation

**Removable module.** `@pem/api` ships in the starter on tRPC 11.x (pinned exact, following tech-stack.md practice), using `@trpc/tanstack-react-query` (not the classic client) and the App Router layout from the tRPC docs, with procedure tiers, an error mapper, and one example domain router whose every procedure is a single `@pem/services` call. It comes with a removal manifest in its README that `yarn verify` can check, for example a structural test asserting that no `@trpc/*` import and no `@pem/api` import remains once the package is removed. `@pem/services` and `@pem/validators` ship as permanent layers. (judgment)

**Tradeoff in a sentence.** You keep the typed, cacheable, native-reachable rail and the convention the agent already knows, and products that don't need it pay one scripted deletion. (judgment)

**Why not the other two.** "Default" (non-removable) charges marketing sites and server-rendered single apps for a cache model they don't use, and it hard-wires `hooks` to the transport. "Absent" throws away a convention two products proved, and it means the first product with a native app re-invents the seam under deadline: exactly the drift scar. (judgment)

**Exit sketch.**

- _Removing tRPC from a product (day one or later):_ delete per the manifest; screens move to RSC reads and Server Actions that call the same services; procedures map one-to-one onto actions or Route Handlers because their bodies are one line. Cost is proportional to the number of client components using `useQuery`, not the number of services. (judgment)
- _Adding tRPC back later:_ copy `packages/api` from the starter, add one router per domain wrapping existing services, mount the route and provider. This is a one-time move with no service changes. (judgment)
- _Leaving tRPC for another RPC (oRPC, Route Handlers plus OpenAPI):_ rewrite `packages/api` and the client call sites; services and validators do not change. (judgment)

**Revisit trigger (observable).**

1. A briefing schedules a React Native app or a second, separately deployed web app: make `@pem/api` mandatory for that product and do not offer removal.
2. The first two products duplicated from the starter both run the removal manifest before first production deploy: change to "absent, add from starter".
3. tRPC publishes a v12 release or an announcement that changes `@trpc/tanstack-react-query` or the fetch adapter: Quartermaster re-scores before any product upgrades.
4. Next.js documents Server Functions as supported for parallel, cacheable client data fetching, or ships a typed client query primitive: re-open the "for" case.
   (judgment)

**Standing exception rails, regardless of the choice.** These are always Route Handlers that call services directly, never tRPC:

- Stripe and other webhooks: `app/api/webhooks/<vendor>/route.ts`, raw-body signature check, idempotency, then the service. CC's `apps/marketing/lib/billing/stripe-webhook/` is the reference.
- AI streaming: `app/api/ai/<feature>/route.ts` with the AI SDK; `@pem/ai` is imported only by services or this route.
- Cron and jobs: `app/api/cron/<job>/route.ts` checking `CRON_SECRET`; queue workers import `@pem/services` directly.\[22\]
- Public or third-party API: versioned `app/api/v1/**/route.ts`, documented with OpenAPI.
- OAuth and auth callbacks: `app/auth/callback/route.ts` (Supabase).
  (judgment; Vercel `CRON_SECRET` behaviour verified, vercel.com docs, 2026-10-03)
