## 2026-10-05 — PEM: Turbo stops hashing env files globally; the sandbox stays shut (EN-15)

`turbo.json` listed `**/.env.*local` and `**/.env` as `globalDependencies`, and the root `build` task listed `.env*` as an input for every package. Turbo hashes those files by reading them, the agent sandbox denies the read, so `yarn check-types`, `yarn test`, `yarn build` and `yarn verify` failed inside it (`I/O error while hashing packages/db/.env.local: Operation not permitted`) as soon as one `.env.local` existed anywhere. Two fixes were weighed.

- **Ruled: Turbo no longer hashes env files globally.** The two globs are gone, and the `.env*` input moved from the root `build` task to `apps/web/turbo.json` (`extends: ["//"]`, `inputs: ["$TURBO_EXTENDS$", ".env*"]`). No other task consumes an env file: `check-types`, `lint` and `test` run `tsc`, `eslint` and `node --test` with no `--env-file`, `apps/docs` reads no variable, and `packages/db/.env.local` feeds only the `db:*` scripts, which are not Turbo tasks. `web#build` keeps the file in its hash because Next loads `apps/web/.env.local` inside the task, where `globalEnv` cannot see it, and the bundle embeds the collapsed `NEXT_PUBLIC_*` values; Turbo's own Next.js example does the same.
- **How a tier change still invalidates the cache.** `globalEnv` lists every variable, so a tier or value set in the shell or on Vercel changes every task's hash. A tier or value changed by editing `apps/web/.env.local` changes `web#build`'s hash through its inputs, and no other task's output can depend on it. One correction in `codebase-conventions.md` §5: `globalEnv` keys the cache on the process environment, not on the file.
- **Rejected: letting the sandbox read the files for Turbo.** Claude Code's sandbox has a read allow-within-deny, but Seatbelt cannot tell `turbo` from `cat`: any allow lets every sandboxed shell command read the values, leaving only the Read-tool deny and bash-guard's text match, which its own header calls "never a boundary". `.claude/settings.json`, `check-settings` and the settings template are unchanged.
- **What stays outside the sandbox:** `yarn build` (verify step 23) on a machine with `apps/web/.env.local`, because `web#build` hashes it on purpose. Taylor's machine holds `packages/db/.env.local` and a root `.env.local` that nothing loads (the example says to copy it to `apps/web/.env.local`), so verify runs sandboxed there today.
- **Proof, in a clean worktree of `agent/STK-3`:** with `packages/db/.env.local` made unreadable, `turbo run check-types --dry` failed on hashing before the change and passed after, and so did `turbo run build --dry`; `turbo run build --dry=json` lists no env file in the global inputs and `.env.local` under `web#build` only when the file exists; `yarn verify` passes. The sandbox denial itself did not reproduce in the session that made this change (its sandbox let the files be read), so the before case rests on the 2026-10-05 observation in `tooling.md` and the unreadable-file run.

## 2026-10-04 — WEB-3: a `contract:run` in flight is not tampered evidence

On 2026-10-04 STK-2's `yarn verify` failed twice with "C1 is PASS, but evidence … changed after it was recorded" while `contract:run STK-8` and then `contract:run STK-10` ran on the shared branch (PR-14). Seconds later it was clean both times. `contract:run` wrote each log as it went, but wrote `results.json` once, after the last criterion. So a ticket with a `yarn verify` criterion also failed on every full run of its own.

- **`contract:run` records each criterion as it finishes** (also made by "PJ: the thread closes its own tickets", below). The log is written to a temp file, renamed into place, and its result is written straight after. The gap between a log and its hash is now one write, not a whole run. PR-16's run lock serialises runs within one checkout; this covers a `yarn verify` outside any run, and another checkout.
- **`check-specs` reads the log's run header on a hash mismatch.** If the header shows a newer run than the recorded one, the PASS is stale: a warning while the ticket is open, and a failure under `--strict` once it has an as-built (PR-15). A matching header, an older one, or none at all is still a hard failure.
- No lock file, so a crashed run cannot leave one behind; such a run leaves a stale PASS, and re-running the criterion clears it.

## 2026-10-04 — WEB-2: the boundaries lint sees `@pem/*` subpath imports

The STK-7 batch review (finding 4), confirmed by probe: `import "@pem/db/client"` in `packages/ui` and `import "@pem/brand/brand"` in `packages/env` linted clean, because eslint-import-resolver-node ignores `exports` and every `@pem/<subpath>` passed as unknown.
